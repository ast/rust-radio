* civlink

WebRTC-based remote control interface for Icom amateur radios (IC-705, IC-7300, etc.).

Provides a browser-based frontend for full radio operation — audio, spectrum, and rig control — over the network using WebRTC for low-latency media transport.

* Features

- Bidirectional audio via WebRTC media tracks (Opus @ 48 kHz)
- Live spectrum display (bins read directly from the radio via CI-V scope data)
- Rig control: frequency, mode, PTT via WebRTC data channels
- Multiple listeners, single controller model — anyone can listen, one operator at a time
- Supports Icom CI-V radios (IC-705, IC-7300, etc.) via the =sidebridge= crate
- User authentication with argon2 password hashing
- TOML-based configuration
- Cross-compiles to aarch64 for Raspberry Pi deployment

* Configuration

Create a =civlink.toml= configuration file:

#+BEGIN_SRC toml
[server]
listen_addr = "0.0.0.0:8080"
frontend_dir = "frontend/dist"

[radio]
url = "tcp://shack:9000"              # or "serial:///dev/ttyUSB0?baud=115200"
audio_device = "USB Audio CODEC"
sample_rate = 48000
#+END_SRC

* User management

Users are stored in the =civlink.toml= config file with argon2-hashed passwords.

#+BEGIN_SRC bash
# Add a user (prompts for password)
civlink -c civlink.toml user-add sm6wjm

# List users
civlink -c civlink.toml user-list

# Remove a user
civlink -c civlink.toml user-remove sm6wjm
#+END_SRC

* Running

#+BEGIN_SRC bash
# Start the server
civlink -c civlink.toml serve
#+END_SRC

Then open =http://localhost:8080= in a browser and log in.

For frontend development with hot reload:

#+END_SRC

* WebRTC: How It Works

This section explains the WebRTC protocol concepts used in civlink. Understanding these helps when debugging connection issues or extending the application.

** Overview

[[https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API][WebRTC]] (Web Real-Time Communication) is a set of browser APIs and protocols for peer-to-peer audio, video, and data transfer with low latency. civlink uses it to stream radio audio bidirectionally and to send rig control commands between the browser and the backend.

** Key Concepts

*** Signaling

Before two WebRTC peers can communicate, they need to exchange connection metadata (SDP offers/answers and ICE candidates). WebRTC does *not* define how this exchange happens — that's called [[https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API/Signaling_and_video_calling#the_signaling_server][signaling]], and it's up to the application.

civlink uses a WebSocket connection (=/ws/signaling=) as its signaling channel. The flow is:

1. Browser creates an =RTCPeerConnection= and generates an SDP offer
2. Offer is sent to the backend over WebSocket
3. Backend creates its own peer connection (via =webrtc-rs=), generates an SDP answer
4. Answer is sent back over WebSocket
5. ICE candidates are exchanged over the same WebSocket

See: [[https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API/Connectivity#signaling][MDN — WebRTC Signaling]]

*** SDP (Session Description Protocol)

[[https://developer.mozilla.org/en-US/docs/Glossary/SDP][SDP]] describes the media capabilities of each peer — codecs supported, transport addresses, media types, etc. In civlink, the SDP negotiation establishes an Opus audio stream.

- *Offer*: "Here's what I can send/receive"
- *Answer*: "Here's what I agree to send/receive"

See: [[https://developer.mozilla.org/en-US/docs/Web/API/RTCSessionDescription][MDN — RTCSessionDescription]]

*** ICE (Interactive Connectivity Establishment)

[[https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API/Protocols#ice][ICE]] is the mechanism WebRTC uses to find the best network path between peers. Each peer gathers *candidates* (possible IP:port combinations) and shares them with the other side. Types of candidates:

- *host*: direct local network address
- *srflx* (server reflexive): public address discovered via a STUN server
- *relay*: traffic relayed through a TURN server (fallback when direct connection fails)

For civlink's typical use case (browser on the local network or VPN connecting to a Pi), host candidates usually suffice. STUN/TURN are needed if operating across NATs.

See: [[https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API/Protocols#ice][MDN — ICE]], [[https://developer.mozilla.org/en-US/docs/Web/API/RTCIceCandidate][MDN — RTCIceCandidate]]

*** Media Tracks

Once the connection is established, audio flows over [[https://developer.mozilla.org/en-US/docs/Web/API/MediaStreamTrack][MediaStreamTracks]]. civlink uses:

- A *receive track* for radio RX audio (backend → browser)
- A *send track* for TX audio / microphone (browser → backend)

Audio is encoded with [[https://developer.mozilla.org/en-US/docs/Web/Media/Formats/Audio_codecs#opus][Opus]] at 48 kHz, which WebRTC supports natively.

See: [[https://developer.mozilla.org/en-US/docs/Web/API/RTCPeerConnection/addTrack][MDN — RTCPeerConnection.addTrack()]]

*** Data Channels

[[https://developer.mozilla.org/en-US/docs/Web/API/RTCDataChannel][RTCDataChannel]] provides a bidirectional channel for arbitrary data over the same peer connection. civlink uses data channels for rig control messages (frequency changes, mode selection, PTT) as JSON.

Data channels can be configured as ordered/unordered and reliable/unreliable. For rig control, civlink uses ordered + reliable (the default) since commands must arrive and in sequence.

See: [[https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API/Using_data_channels][MDN — Using WebRTC Data Channels]]

** Debugging Tips

- Check the browser console for ICE connection state changes (=iceConnectionState=)
- If the connection stalls at "checking", ICE candidates aren't getting through — check firewall/NAT
- Use =chrome://webrtc-internals= (Chrome) or =about:webrtc= (Firefox) to inspect peer connections, codecs, and packet stats
- The backend logs ICE state transitions via =tracing= — run with =RUST_LOG=civlink=debug=
